# low-vertex-flat-tori

Numerically discovering **flat, embedded 8-vertex tori**, following Rich Schwartz's
vertex-minimal construction (`rich/`).

A flat torus is intrinsically a flat sheet ℝ²/Λ. The challenge is realizing one with only
**8 vertices** as a straight-edge polyhedron in ℝ³ that is both *flat* (every vertex has cone
angle exactly 2π) and *embedded* (no two triangles cross). There are **7 combinatorial types**
of 8-vertex torus triangulation (each V=8, E=24, F=16); only type **#7** (Rich's) is
degree-6-regular — the other six mix degree 5/7, so nothing in the pipeline assumes degree 6.

## The mathematics, in layers

The repository is organized so the code reads like the mathematics. Three objects, each built on
the one before — see **[`docs/math/`](docs/math/)** for the full write-up of each:

1. **The torus** — the *topology* (a genus-1 surface). It is never an object, just the fact that
   `V − E + F = 0`; everything here is a torus.
2. **A [triangulation](docs/math/triangulation.md)** — the *discrete topology*: a combinatorial
   structure realizing the torus. Pure combinatorics (edges, vertex links, dual graph), all
   derived from a triangle list. There are 7 combinatorial types on 8 vertices.
3. **A [marking](docs/math/marking.md)** — a *decoration* on a triangulation: a compact
   fundamental domain (how to cut and unroll it) and a basis of `H₁` (the τ-generators). Computed
   once — minimum-cut domain, centered-spiral unroll order, cut-aligned homology generators — and
   stored on the triangulation.

Given a triangulated flat torus **and a marking**, the **developing map** (`src/math/develop.ts`)
unfolds it into the plane and reads its modulus **τ ∈ ℍ** — its point in **Teichmüller** space.
Forgetting the marking — the `SL(2,ℤ)` quotient, `reduceModulus` — projects to **moduli** space.
The marking is exactly what distinguishes the two.

## Layout

```
src/tori/        The 7 triangulations + the Triangulation builder (all derived & Euler-checked).
src/math/        Pure math — no three.js, no DOM. The engine.
src/mesh/        Triangulation → three.js geometry (faces, edges, lattice UVs).
src/render/      Path-traced Studio (WebGL preview ↔ three-gpu-pathtracer).
src/viewer/      Older lightweight three.js viewer (TorusView) + palettes.
src/io/          CSV ⇄ PaperTorus.
demos/           Per-demo browser entry points (one main.ts each).
scripts/         Node CLI tools (sampling, search, validation, marking).
data/            CSV result sets (one torus per row, 24 floats).
docs/            docs/math/ (this system, mathematically) + design plans + figures.
rich/            Rich Schwartz's reference papers (PDFs) and original code.
```

The dependency rule: `src/math/` and `src/tori/` never import three.js or touch the DOM, so
every algorithm runs headless under `tsx` in `scripts/`. Rendering (`src/mesh`, `src/render`,
`src/viewer`) and the demos sit strictly on top.

### Key modules (`src/math/` + `src/tori/`)

| File | Role |
| --- | --- |
| `../tori/triangulation.ts` | `Triangulation` builder — links, dual adjacency, all derived from the triangle list and validated by `V−E+F=0`. Attaches each triangulation's **marking**. |
| `../tori/markings.ts` | the cached markings (`cut`, `developOrder`, `generatorLoops`), generated by `npm run compute-markings`. |
| `marking.ts` | `canonicalMarking` — minimum-cut domain + centered-spiral order + cut-aligned `H₁` generators. The expensive marking computation. |
| `exactMinCutDomain` (`exactDomain.ts`) | the provably-minimal fundamental domain (fewest boundary edges). |
| `harmonicLayout.ts` | discrete-harmonic embedding into a flat torus ℝ²/Λ — the period lattice + integer period-jump cocycle used to pick generators. |
| `embedding.ts` | `PaperTorus`: 8 vertex positions in ℝ³ (a `Float64Array` of 24). |
| `angles.ts` | Cone-angle sums and deficits (2π − coneAngle). The flatness residual. |
| `newton.ts` | `newtonFlatten` — min-norm Gauss–Newton projection onto the flatness manifold. |
| `embedded.ts` | `isEmbedded` / `firstViolation` — triangle–triangle intersection test. |
| `energies/` | Pluggable `RepulsionEnergy` objects (chord², cut-off-area, cell-margin, …) consumed by the flow. |
| `embeddedFlow.ts` | Alternating "Newton — gradient step — Newton" descent on a repulsion energy. |
| `develop.ts` | Unfold the triangulation into the plane via its marking; read the modulus τ ∈ ℍ (and `reduceModulus` into the fundamental domain). |
| `normalize.ts` | Canonical pose under the ℝ³ similarity group (7 DOF → 17 reduced coords). |

## Two pipelines

**1. Discovery — find a flat embedded torus.** `scripts/sample-flat.mjs`: sample a seed →
`newtonFlatten` (land on the flatness manifold) → `embeddedFlow` (descend a repulsion energy,
re-flattening each step) → verify `maxConeDeficit < tol` **and** `isEmbedded`. Accepted tori
are written as CSV rows.

**2. Develop — compute the modulus τ.** `develop.ts` unfolds a flat torus along its marking and
reads the holonomy of the two generator loops to get its point τ ∈ ℍ in Teichmüller space.
Validate the whole develop pipeline with:

```
npx tsx scripts/develop-check.mjs [path/to.csv]   # defaults to data/explore-from-seeds/seeds.csv
```

It asserts covolume = intrinsic area, rotational defect ≈ 0, and cone deficit ≈ 0 on Rich +
every row, then prints τ and its SL(2,ℤ)-reduced τ̂.

> **Note on strategy.** An alternative "paper-sheet" reformulation (realize edge lengths from a
> flat lattice chart with τ as an input dial) was **explored and set aside** — it underperformed
> the flatten-first pipeline in practice. The discovery pipeline above is the committed approach.

## Running

Install once: `npm install`.

```
npm run dev <demo>        # serve a demo (vite). Omit <demo> to list them.
npm run build <demo>      # self-contained build → dist/<demo>/
npm run preview <demo>
npm run compute-markings  # recompute & save the markings (after adding/changing a triangulation)
```

> `npm run dev <demo>` writes a private entry to `.dev/<demo>.html` (gitignored) and serves it on
> a **stable per-demo port** (a hash of the name, in 5200–5599) — so each demo always lives at the
> same URL and two demos never collide. Run them in separate terminals in parallel; re-running a
> demo that's already up just prints its URL. `build`/`preview` still rewrite the tracked
> `index.html`, so `git status` shows `index.html` modified after a build.

Run `npm run dev` with no name to list all available demos.

### Search / data scripts

```
npm run sample      -- [opts]   # rejection-sample embedded then flat tori → .bin
npm run sample-flat -- [opts]   # full Newton + repulsion-flow search → .csv
npm run fatten      -- [opts]   # push already-flat samples to a larger embedding margin
```

Each script documents its flags in a header comment (`--help`-style). Run with `npx tsx`.

## Data format

CSV result files (`data/`): **one torus per line, 24 comma-separated full-precision floats** in
`x0,y0,z0, x1,y1,z1, …, x7,y7,z7` order — exactly a `PaperTorus`'s `positions`. Values round-trip
to their double-precision representation. The `.bin` files from `scripts/sample-embedded.mjs` are
Float32, same 24-float packing (96 bytes/sample). A row records only points — interpret it by
pairing with a chosen triangulation.

## Normalization convention

`src/math/normalize.ts` puts an 8-vertex torus into a **canonical pose** under the similarity
group of ℝ³ (translation ⊕ rotation ⊕ uniform scale = 7 continuous degrees of freedom). This is
the project-wide convention; use it whenever a torus needs a canonical representative.

`normalize(p)` does, in order:

1. **Translate** so vertex 0 is at the origin.
2. **Rotate + uniformly scale** so vertex 1 is at (1, 0, 0) — scale by 1/|v₁−v₀|, then rotate that
   direction onto the +x axis.
3. **Rotate about the x-axis** so vertex 2 lies in the xy-plane (z₂ = 0), choosing the half-turn
   that puts it on the +y side (**y₂ ≥ 0**).

The three **anchor vertices** are then pinned to v₀ = (0,0,0), v₁ = (1,0,0), v₂ = (x₂, y₂, 0) with
y₂ ≥ 0. This removes exactly the 7 similarity DOF, so the free data is **24 − 7 = 17** numbers.
`toReduced(p)` returns those 17; `fromReduced(r)` rebuilds the full 24. Only **proper** rotations
are used, so chirality is preserved, not quotiented.
